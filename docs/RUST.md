# Rust Integration

> **Status**: v0.3 — *Rust Adoption* — released.
> The Rust subsystem is integrated into the kernel build and ships the first ported subsystem (heap allocator). The C kernel is unaffected by its presence except at the explicit FFI boundary.

## Motivation

Munux began as a C and Assembly project, and those two languages remain the right tools for the work they do today — the bootloader, interrupt stubs, the context switch, and the well-established core subsystems. Introducing Rust is **not** a rewrite. It is a deliberate, scoped expansion of the toolchain to gain three properties that are difficult to obtain in C:

1. **Compile-time memory safety** — ownership and borrowing eliminate use-after-free, double-free, and data races at the language level.
2. **Stronger types at zero cost** — `Option`, `Result`, exhaustive matches, and newtype wrappers express invariants the compiler can enforce.
3. **A modern dependency story for low-level code** — small, audited `no_std` crates (such as `bitflags`, `spin`, `linked_list_allocator`) are available without dragging in a runtime.

These benefits matter most where memory bugs are most damaging — allocators, parsers (filesystem metadata, ELF headers, network packets), and data structures shared across interrupt context. These subsystems are the natural first homes for Rust in Munux.

## Non-Goals

To keep this work honest and focused, the following are explicitly **out of scope** for the Rust adoption:

- **Replacing the bootloader or interrupt stubs.** Assembly remains the only sane tool for those layers.
- **Wholesale rewrite of working C code.** A subsystem is ported only when there is a concrete justification (memory safety, planned major rework, or test surface improvement).
- **Introducing the Rust standard library.** The kernel is `no_std`. Only `core` and `alloc` are available.
- **Adopting `async` or any runtime.** Munux has its own cooperative and preemptive scheduling model.
- **Pulling in unaudited third-party crates.** Each dependency is reviewed and pinned by exact version.

## High-Level Architecture

```mermaid

    end

    KMAIN -->|calls| HDR

    SAFE -. "GlobalAlloc shim" .-> HEAP_C

    class SHIM,SAFE rust
```

The Rust workspace produces one static library, `libmunux_rs.a`. The C kernel includes the generated header `munux_rs.h` and calls Rust functions exactly as it would call any other C function — there is no special calling convention, no thunk, no shim emitted by the linker.

The two crates inside the workspace serve distinct roles:

- **`munux-rs-ffi`** is the trust boundary. Every `unsafe` block, every `extern "C"` export, and the panic handler live here. This crate is small and easy to audit.
- **`munux-rs`** is the safe-Rust portion where actual logic is implemented. It forbids unsafe operations outside of narrowly justified exceptions, each carrying a `// SAFETY:` rationale.

## Toolchain

| Tool | Purpose | Pinned by |
|---|---|---|
| `rustup` | Toolchain manager | User installs once |
| `rustc` (nightly) | Compiler — required for `-Z build-std` and custom targets | `rust-toolchain.toml` |
| `cargo` | Build orchestration | Bundled with `rustc` |
| `rust-src` component | Source for `core` / `alloc` to rebuild for the target | `rust-toolchain.toml` |
| `clippy` | Linter (warnings → errors in CI) | `rust-toolchain.toml` |
| `rustfmt` | Formatter (enforced in CI) | `rust-toolchain.toml` |
| `cbindgen` | Generates C headers from the Rust public API | `Cargo.toml` (`cargo install` recipe) |

The nightly channel is required only because the kernel must rebuild `core` and `alloc` with `-Z build-std`. There is an open RFC to stabilize this; if it lands, Munux will move to stable Rust the day the feature is available.

## Custom Target

The kernel target is `i686-unknown-none`, defined by a JSON specification at `kernel/rust/i686-unknown-none.json`:

```json
{
  "llvm-target": "i686-unknown-none",
  "data-layout": "e-m:e-p:32:32-p270:32:32-p271:32:32-p272:64:64-f64:32:64-f80:32-n8:16:32-S128",
  "arch": "x86",
  "target-endian": "little",
  "target-pointer-width": "32",
  "target-c-int-width": "32",
  "os": "none",
  "executables": true,
  "linker-flavor": "ld.lld",
  "linker": "rust-lld",
  "panic-strategy": "abort",
  "disable-redzone": true,
  "features": "-mmx,-sse,+soft-float",
  "relocation-model": "static",
  "code-model": "kernel"
}
```

Key choices:

- **`panic-strategy: abort`** — Unwinding requires runtime machinery the kernel does not have. A panic must terminate the offending path immediately, routed through the kernel's existing panic infrastructure.
- **`-mmx,-sse,+soft-float`** — The kernel does not save FPU/SIMD state at context switches. Rust must not emit instructions that touch those register files.
- **`relocation-model: static`** — Matches the C side's `-fno-pic -fno-pie`. The kernel runs at a fixed virtual address.
- **`disable-redzone: true`** — A red zone is unsafe in any context where interrupts can preempt and clobber stack memory below `%esp`.

## Build Integration

The top-level `Makefile` orchestrates the multi-language build. The Rust phase is a single recipe:

```makefile
RUST_DIR        = $(KERNEL_DIR)/rust
RUST_TARGET     = i686-unknown-none
RUST_PROFILE    = release
RUST_TARGET_DIR = $(RUST_DIR)/target/$(RUST_TARGET)/$(RUST_PROFILE)
RUST_LIB        = $(RUST_TARGET_DIR)/libmunux_rs.a

$(RUST_LIB): $(shell find $(RUST_DIR) -name '*.rs' -o -name 'Cargo.toml')
	@echo "🦀 Building Rust static library..."
	cd $(RUST_DIR) && cargo build --release \
	    --target $(RUST_TARGET).json \
	    -Z build-std=core,alloc

# The final link consumes libmunux_rs.a as one more input.
$(KERNEL_ELF): $(KERNEL_OBJS) $(RUST_LIB)
	$(LD) $(LDFLAGS) -o $@ \
	    $(BUILD_DIR)/multiboot.o \
	    $(filter-out $(BUILD_DIR)/multiboot.o,$(KERNEL_OBJS)) \
	    $(RUST_LIB)
```

Convenience targets:

| Target | Effect |
|---|---|
| `make rust` | Build only `libmunux_rs.a` |
| `make rust-check` | `cargo check` + `cargo clippy -- -D warnings` |
| `make rust-test` | Run host-target unit tests (pure-logic modules only) |
| `make rust-fmt` | `cargo fmt --check` (CI gate) |
| `make rust-clean` | `cargo clean` in the Rust workspace |

The Rust phase parallelizes with the C/Assembly phases under `make -j`, since the outputs are independent until the final `ld` invocation.

## FFI Conventions

Every function crossing the boundary follows a small, predictable contract.

**On the Rust side (`munux-rs-ffi/src/lib.rs`):**

```rust
/// Allocates `size` bytes from the kernel heap with `align` alignment.
///
/// Returns a null pointer on failure.
///
/// # Safety
/// The caller must eventually free the returned pointer with
/// `munux_rs_free`, passing the same size and alignment used here.
#[no_mangle]
pub unsafe extern "C" fn munux_rs_alloc(size: usize, align: usize) -> *mut u8 {
    // SAFETY: We forward to the audited safe-Rust implementation.
    munux_rs::alloc::allocate(size, align)
}
```

**On the C side (`kernel/rust/include/munux_rs.h`, generated by `cbindgen`):**

```c
/* Generated by cbindgen — do not edit by hand. */
uint8_t *munux_rs_alloc(size_t size, size_t align);
void     munux_rs_free(uint8_t *ptr, size_t size, size_t align);
```

Rules enforced by code review:

1. Every exported function name is prefixed `munux_rs_`.
2. Every exported function uses C-compatible primitive types or `#[repr(C)]` structs — no Rust enums, no `&str`, no `String`, no trait objects.
3. Every exported function is `pub unsafe extern "C" fn` and documents its safety contract.
4. Generated headers (`include/`) are committed to the repository so a reviewer can diff API changes without running `cbindgen`.
5. Any change to an exported signature requires regenerating the header in the same commit.

## Allocator Contract

Rust needs a global allocator to use `alloc::boxed::Box`, `alloc::vec::Vec`, and friends. Rather than introducing a second heap, the Rust side **wraps the existing kernel heap** through a `GlobalAlloc` shim:

```rust
// In munux-rs-ffi
extern "C" {
    fn kmalloc(size: usize) -> *mut u8;
    fn kfree(ptr: *mut u8);
}

struct KernelHeap;

unsafe impl GlobalAlloc for KernelHeap {
    unsafe fn alloc(&self, layout: Layout) -> *mut u8 {
        // SAFETY: kmalloc is the kernel's audited allocator; alignment
        // requirements above MIN_ALIGN are handled by a small adjustment.
        unsafe { kmalloc(layout.size()) }
    }
    unsafe fn dealloc(&self, ptr: *mut u8, _layout: Layout) {
        unsafe { kfree(ptr) }
    }
}

#[global_allocator]
static ALLOCATOR: KernelHeap = KernelHeap;
```

This single heap is essential during the v0.3 transition: it lets the heap allocator be ported to Rust **incrementally**. The C entry points `kmalloc` / `kfree` remain stable, while their implementations are progressively re-routed to safe Rust internals.

## Panic Handling

The Rust `#[panic_handler]` routes a Rust panic through the existing kernel panic path so the experience is identical from the user's perspective:

```rust
// In munux-rs-ffi/src/panic.rs
use core::panic::PanicInfo;

extern "C" {
    fn serial_writestring(port: u16, s: *const u8);
    fn kernel_panic(msg: *const u8) -> !;
}

#[panic_handler]
fn panic(info: &PanicInfo) -> ! {
    // A small inline formatter writes the message to COM1 first,
    // then hands off to the kernel's panic routine which halts the CPU.
    // SAFETY: serial_writestring and kernel_panic are kernel entry
    // points expecting NUL-terminated C strings.
    unsafe {
        serial_writestring(0x3F8, b"RUST PANIC: \0".as_ptr());
        // ... write info.message() / info.location() ...
        kernel_panic(b"Rust panic\0".as_ptr())
    }
}
```

Combined with `panic-strategy: abort` in the target spec, this guarantees no unwinding tables are emitted and the binary size stays small.

## Safety Policy

The Rust crate root enforces:

```rust
#![no_std]
#![forbid(unsafe_op_in_unsafe_fn)]
#![deny(clippy::undocumented_unsafe_blocks)]
#![deny(clippy::missing_safety_doc)]
#![warn(clippy::pedantic)]
```

Practical consequences:

- A function marked `unsafe fn` does **not** automatically allow `unsafe` operations inside its body. Each must be in an explicit `unsafe { … }` block.
- Every `unsafe` block must carry a `// SAFETY:` comment explaining the invariant being relied upon.
- The `munux-rs` crate contains zero `unsafe` blocks under normal review; exceptions require a written justification in the commit message and reviewer sign-off.
- All `unsafe` lives in `munux-rs-ffi`, which is small enough to audit in a single sitting.

## Porting Plan

Subsystems migrate to Rust **only when there is a concrete payoff**. The v0.3 work targets one subsystem; later phases will be opportunistic.

### v0.3 — Heap Allocator (Completed)

The heap allocator was the chosen first port because:

- Its API surface (`kmalloc`, `kfree`) is small and stable.
- Memory bugs in an allocator manifest as silent corruption elsewhere — exactly the failure class Rust prevents.
- It can be benchmarked deterministically, making regression detection easy.

Outcome:

- [`heap.rs`](../munux-core/kernel/rust/munux-rs/src/heap.rs) implements the first-fit free list with adjacent-block coalescing, the `#[repr(C)]` block header matches the legacy `heap_block_t` byte-for-byte, and the allocator is protected by an `IrqMutex<T>` that pairs a spin-lock with `cli` / `sti`.
- [`heap.c`](../munux-core/kernel/memory/heap.c) is now a thin wrapper: it owns the initial page mapping via PMM / VMM, exposes a `munux_c_heap_grow` callback, and forwards `kmalloc` / `kfree` to the Rust FFI exports.
- The legacy C entry points are byte-compatible — no caller had to change.

### v0.4 — Opportunistic Ports During System Services Work

As Phase 2 introduces VFS and ext2, parsers for on-disk metadata (superblocks, inodes, directory entries) are excellent candidates for Rust:

- They consume untrusted on-disk data — a classic memory-bug surface.
- They are stateless and easy to test.
- They have no real-time constraints.

### Long Term — New Code Defaults to Rust

Once the toolchain is bedded in, the default for new subsystems shifts: **new code is written in Rust unless there is a specific reason to use C or Assembly**. Existing working C is left alone unless it is being substantially reworked anyway.

## Testing Strategy

Two test surfaces:

**Host-target unit tests** — Pure-logic modules (data structures, parsers, bit manipulation) live in modules that compile both for the kernel target and the developer's host. The host target enables `cargo test`, fast iteration, and tools like `miri` for undefined-behavior detection.

**In-kernel smoke tests** — A `tests/` directory under `munux-core/` contains kernel-side test routines that exercise the Rust subsystem in a QEMU boot. These run as part of `make test` and verify the FFI contract end-to-end.

## CI Gates

Every commit must pass, in order:

1. `cargo fmt --check` — Formatting is mechanical and non-negotiable.
2. `cargo clippy --all-targets -- -D warnings` — All clippy lints are errors.
3. `cargo build --release --target i686-unknown-none.json -Z build-std=core,alloc` — The kernel target must compile cleanly.
4. `cargo test` (host target) — Host-runnable unit tests must pass.
5. `make` (full kernel build) — The final ELF must link.
6. `make run` smoke test in QEMU — The kernel must boot and the Rust subsystem must initialize without panicking.

## Lessons From the v0.3 Integration

A handful of details only became obvious when the build was actually exercised end-to-end. They are recorded here so the next contributor does not relearn them:

- **`-mno-sse -mno-sse2 -mno-mmx -mgeneral-regs-only` are mandatory on the C side.** Without them, GCC `-O2` happily vectorizes `memset`/`memcpy` with SSE2 (`movd`, `punpcklbw`, `pshufd`). The kernel never enables SSE in `CR0`/`CR4`, so the first vectorized op triggers `#UD`/`#NM`, which cascades to a triple-fault and CPU reset. The Rust side already disables these features via the custom target spec; the C side has to match.
- **Target-spec JSON syntax has drifted.** Recent nightlies require `target-pointer-width` and `target-c-int-width` to be integers (not strings), need `i128:128` in the data-layout, and reject `+soft-float` as an explicit feature (use the `-mmx,-sse,...` disable list instead). The `.cargo/config.toml` also needs `json-target-spec = true` under `[unstable]`.
- **`cargo clippy --all-targets` will try to build the kernel-target test harness, which has no `test` crate and no panic handler.** Use `cargo clippy --lib` instead.
- **Pre-v0.3 there was a latent bootstrap bug in `vmm_init`** — it allocated the page directory through `kmalloc_aligned`, which depended on the heap, which depended on the VMM. The bug was harmless only because `kernel_main` never actually called the init functions. v0.3 wiring exposed it; the fix is to take the PD straight from a physical frame.

## Open Questions

These are recorded honestly as known unknowns rather than buried:

- **Alignment in the `GlobalAlloc` shim.** `kmalloc` currently aligns to `sizeof(void *)`. Allocations requiring higher alignment (cache lines, page boundaries) need either a richer `kmalloc` or a separate aligned-alloc path. The current `kmalloc_aligned` over-allocates by a page and rounds up; a proper aligned-alloc API is a v0.4 candidate.
- **Stable-channel migration.** The plan is to track the `build-std` stabilization RFC and move off nightly as soon as feasible.
- **Floating-point in user mode.** When user mode arrives, the FPU will need lazy save/restore. The kernel-wide no-SIMD policy still applies; user mode handling is a separate design discussion.
- **Memory discovery.** `pmm_init(0x02000000)` currently hard-codes 32 MiB to match the QEMU default. Reading the multiboot info structure to get the real `mem_upper` is a v0.4 task.
